# Мультиагентный процесс Codex: установка и работа в проекте

[English version](WORK_FLOW.md)

В этом руководстве описано, как установить процесс в конкретный проект, какие файлы изменяет установщик, как Codex использует эти файлы, как проверить установку и как безопасно удалить процесс.

## Что предоставляет установка

Текущая версия устанавливает контракты процесса на уровне проекта. Они определяют, как Codex классифицирует задачи, когда составляет план, как ограничивает область реализации, какие доказательства необходимы, когда требуется независимая проверка и в каких случаях разрешены операции публикации Git.

В текущую версию входят:

- инструкции проекта через `AGENTS.md`;
- правила маршрутизации, валидации, эскалации и безопасной работы с Git;
- шаблоны контекста проекта, задачи, активного плана и передачи работы;
- транзакционные установщик и деинсталлятор;
- контроль управляемых файлов по SHA-256;
- откат прерванных операций;
- подключаемый каталог из девяти пользовательских агентов уровня проекта;
- автономная проверка TOML и схемы, а также необязательная живая диагностика обнаружения.

Установка только контрактов остаётся режимом по умолчанию. Чтобы проверить и установить девять файлов `.codex/agents/*.toml`, используйте `-WithCustomAgents` в Windows или `--with-custom-agents` в Linux/macOS.

Пользовательские агенты пока включаются явно; допустимость установки и приёма доказательств указана в текущей политике версий.

<!-- codex-policy-reference:begin -->
Текущая политика версий: [сводка по реестру](codex_version.md#current-version-policy).
Готовность релиза: **NOT_READY**; provenance обслуживающего backend и действующей
политики: **BLOCKED**. Runtime не подтверждён ни для одной зарегистрированной версии.
<!-- codex-policy-reference:end -->

Изоляция ролей также является многоуровневым ограничением, а не абсолютной границей безопасности: настройки родительского сеанса могут переопределять значения агента, а режим чтения файлов сам по себе не предотвращает все внешние побочные эффекты.

При установленных пользовательских агентах:

- новый сеанс Codex загружает проектные TOML-файлы и может выбирать именованные роли с заданными моделями, уровнем рассуждения, песочницей и инструкциями;
- исследователь, архитекторы, валидатор и ревьюер по умолчанию используют `read-only`;
- исполнители, агент эскалации и агент Git-публикации используют `workspace-write`, но ограничены назначенными файлами и явной авторизацией;
- корневой агент по-прежнему отвечает за маршрутизацию, состояние выполнения, интеграцию и итоговые доказательства;
- статическая проверка подтверждает согласованность файлов и схемы, а необязательная живая диагностика лишь собирает возможные свидетельства обнаружения и пока не может сертифицировать его в среде выполнения;
- поведенческие гарантии прав остаются неподтверждёнными до выполнения полной матрицы тестов в изолированном проекте.

Установка, обновление, восстановление и удаление ограничены целевым проектом. Глобальная конфигурация Codex не изменяется, а конфликт с неуправляемым проектным агентом останавливает операцию до записи файлов.

Для Codex `0.159.3` приняты доказательства L0-L6 по закрытым источникам: L5 охватывает девять ролей и 18 сеансов; все пять проверок L6 прошли независимую проверку и рецензирование. Последний набор: 54 успешных теста, проверенных независимо. Привязка задания L8 восстановлена через неизменяемый манифест в нативных инструкциях. Explorer: PASS; quick implementer: FAIL, поскольку вместо запрошенного workspace-write у родителя и дочернего агента наблюдается read-only. Модель и effort совпадают; оставшиеся семь проверок L8 не запускались после сбоя. L7 не принят, L9-L13 ещё не запускались. Общий статус **NOT READY**, `runtimeValidated: false`. Прежний запуск `eb2062b6-6307-4012-8806-a602d7fe9d57` относится к 0.159.0. См. [отчёт](docs/validation/codex-0.159.3-windows.md) и [план](plan/plan_validated_finis.md).

## Область установки

Установка выполняется только в один указанный проект. Глобальный каталог Codex не изменяется.

```text
репозиторий пакета процесса
        |
        | install.ps1 или install.sh
        v
целевой проект
  |-- AGENTS.md                         добавляется управляемый блок
  |-- .codex/agents/*.toml              необязательные пользовательские агенты
  |-- .codex-workflow/                  копии контрактов
  |-- docs/ai/PROJECT_CONTEXT.md        редактируемый контекст проекта
  |-- plans/TASK_TEMPLATE.md            шаблон пакета задачи
  `-- .hybrid-codex-workflow-state.json состояние установки
```

Слово `hybrid` сохраняется во внутренних именах состояния, журнала, резервных копий, схем и маркеров только ради совместимости с предыдущими установками. Не переименовывайте эти идентификаторы вручную.

## Требования

Перед установкой убедитесь, что:

1. Репозиторий процесса скачан или клонирован локально.
2. Каталог целевого проекта уже существует.
3. Доступен Python 3; для установки пользовательских агентов требуется Python 3.11 или новее.
4. Codex CLI доступен через `PATH`.
5. `codex --version` соответствует записи реестра, разрешённой для статической установки в текущей политике версий.
6. У вас есть права на запись в целевой проект.

Проверка в Windows PowerShell:

```powershell
python --version
codex --version
Test-Path -LiteralPath "C:\path\to\codex-multi-agent-workflow\install.ps1"
Test-Path -LiteralPath "C:\path\to\your-project"
```

Проверка в Linux/macOS:

```bash
python3 --version
codex --version
test -f "/path/to/codex-multi-agent-workflow/install.sh"
test -d "/path/to/your-project"
```

Пример вывода для предпочтительной версии статической установки:

<!-- codex-current-target-example:begin -->
```text
codex-cli 0.160.0
```
<!-- codex-current-target-example:end -->

Если версия Codex не поддерживается или не определяется, установщик завершится до изменения файлов проекта.

## Установка в Windows

Откройте PowerShell в репозитории пакета процесса.

### Шаг 1. Предварительный просмотр

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project" -WhatIf
```

Предварительный запуск проверяет требования, версию, исходные файлы, пути, символические ссылки, состояние и маркеры. Он выводит запланированные операции, но ничего не записывает.

Для нового проекта должны быть показаны установка контрактов, контекста проекта, шаблона задачи, управляемого блока `AGENTS.md` и манифеста состояния.

### Шаг 2. Установка

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project"
```

Для предварительного просмотра и установки пользовательских агентов:

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project" -WithCustomAgents -WhatIf
.\install.ps1 -TargetRepository "C:\path\to\your-project" -WithCustomAgents
```

Успешная операция завершается сообщением:

```text
PASS: Codex Multi-Agent Workflow installed in C:\path\to\your-project
```

Если параметр `-TargetRepository` не задан, используется текущий каталог:

```powershell
Set-Location "C:\path\to\your-project"
C:\path\to\codex-multi-agent-workflow\install.ps1
```

### Шаг 3. Настройка контекста проекта

Откройте `docs/ai/PROJECT_CONTEXT.md` в целевом проекте и замените заполнители реальными данными:

- приложения и сервисы;
- границы модулей;
- публичные API;
- правила аутентификации и авторизации;
- команды сборки, тестирования, линтинга и проверки типов;
- побочные эффекты команд;
- операции, влияющие на production;
- соглашения по коду;
- файлы, которые Codex не должен изменять.

Не сохраняйте в этом файле секреты, токены, пароли, закрытые ключи или полные строки подключения.

### Шаг 4. Новый сеанс Codex

Codex формирует цепочку инструкций `AGENTS.md` при запуске команды или TUI-сеанса. После установки перезапустите существующий сеанс.

```powershell
codex --cd "C:\path\to\your-project"
```

Правила обнаружения проектных инструкций описаны в официальной документации OpenAI [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

## Что установщик делает внутри

Установка выполняется в следующем порядке:

1. Оболочка PowerShell или Bash находит Python 3.
2. `scripts/workflow_manager.py` преобразует целевой путь в абсолютный.
3. Отклоняются корень файловой системы, символическая ссылка в качестве цели, выход за пределы проекта и управляемые пути через символические ссылки.
4. Проверяется, что все обязательные исходные файлы пакета существуют и являются обычными файлами.
5. Выполняется `codex --version`; неподдерживаемая версия отклоняется.
6. Если запрошены пользовательские агенты, до планирования записи проверяются все девять TOML-файлов по `compatibility/codex-agents.json`.
7. Проверяется наличие журнала прерванной транзакции.
8. При повторной установке загружается и строго проверяется существующий манифест состояния.
9. Каталог `.codex-workflow/` без манифеста состояния считается содержимым с неизвестным владельцем и не перезаписывается.
10. Конфликтующий неуправляемый `.codex/agents/*.toml` отклоняется; идентичный существующий агент сохраняется как принадлежащий проекту.
11. Для исходных и установленных файлов вычисляются SHA-256 хэши.
12. Планируются новые файлы, безопасные обновления и сохранение изменённых пользователем файлов.
13. В `AGENTS.md` добавляется или обновляется один маркированный блок без замены остальных инструкций проекта.
14. Журнал транзакции записывается и строго проверяется до создания любой постоянной подготовительной резервной копии.
15. Создаются необходимые резервные копии; их владелец, пути и хэши сверяются с журналом.
16. Перед каждой операцией в журнале фиксируется состояние `applying`; изменение выполняется через временный файл в том же каталоге и атомарную замену, после чего проверяется итоговый хэш и фиксируется состояние `applied`.
17. Манифест состояния записывается и проверяется последним, после чего транзакция отмечается как завершённая (`committed`).
18. Выполняется очистка завершённой транзакции; прерванную очистку журнала и резервных копий можно безопасно продолжить.

При ошибке до фиксации транзакции восстановление откатывает применённые операции в обратном порядке по проверенным данным. Если транзакция уже зафиксирована, восстановление не отменяет установленное состояние, а завершает очистку. Если откат или очистку нельзя безопасно завершить, журнал и подтверждающие данные сохраняются для явного восстановления.

Проверки путей отклоняют существующие символические ссылки, точки соединения (`junction`) и другие точки повторного анализа (`reparse point`) в целевых путях и их родительских каталогах. Однако проверки основаны на именах путей и не закрывают состязательную TOCTOU-атаку с одновременной подменой родительского каталога в Windows. До появления проверенного Win32-механизма с операциями относительно дескриптора либо явного решения по модели угроз используйте только доверенную локальную файловую систему и не заявляйте полную защиту от таких атак.

## Файлы в целевом проекте

### `AGENTS.md`

Установщик добавляет блок с совместимыми маркерами:

```markdown
<!-- hybrid-codex-workflow:start -->
## Codex multi-agent workflow

- Read `.codex-workflow/CODEX_WORKFLOW.md` and the applicable files under `.codex-workflow/rules/` before routing or implementing work.
- Use `docs/ai/PROJECT_CONTEXT.md` for project-specific architecture, commands, and boundaries.
- If `.codex/agents/*.toml` is present, use the named role definitions for delegation; treat their sandbox values as defaults subject to parent-session controls.
- For non-trivial work, the root orchestrator exclusively owns `plans/ACTIVE_PLAN.md` and `plans/HANDOFF.md`.
- Preserve unrelated changes, require observed validation evidence, and never infer commit or push authorization.
<!-- hybrid-codex-workflow:end -->
```

Если `AGENTS.md` уже существует, его содержимое сохраняется, а блок добавляется в конец. Повторная установка обновляет неизменённый блок со старым названием. Изменённый пользователем управляемый блок сохраняется и не перезаписывается.

### `.codex-workflow/`

Каталог содержит управляемые установщиком копии:

```text
.codex-workflow/
  CODEX_WORKFLOW.md
  rules/
    ROUTING.md
    VALIDATION.md
    ESCALATION.md
    GIT_SAFETY.md
  templates/
    PROJECT_CONTEXT.md
    ACTIVE_PLAN.md
    HANDOFF.md
    TASK_TEMPLATE.md
  timeline/
    timeline_cli.py
    timeline_collector.py
    timeline_exporter.py
    timeline_privacy.py
    timeline_schema.py
```

Считайте эти файлы управляемыми пакетом. Проектные данные должны находиться в `docs/ai/` и `plans/`, а не в `.codex-workflow/`.

### Необязательная временная шкала выполнения

Установщик включает явную запись временной шкалы. Она не отслеживает сеансы
Codex автоматически. Начните и завершите ход вручную, затем просмотрите или
экспортируйте журнал задачи:

```powershell
python .\.codex-workflow\timeline\timeline_cli.py start --task-id <task-id> --stage IMPLEMENTATION --agent-role root --summary "Реализовать проверку запроса"
python .\.codex-workflow\timeline\timeline_cli.py finish --task-id <task-id> --turn-id 0 --status SUCCESS --summary "Реализация и проверка завершены"
python .\.codex-workflow\timeline\timeline_cli.py show --task-id <task-id>
python .\.codex-workflow\timeline\timeline_cli.py show --task-id <task-id> --format json --output timeline.json
```

Если команда запускается вне каталога проекта, укажите `--project <path>`
перед подкомандой. Команда `start` выводит идентификатор хода для `finish`.
Записи хранятся в `.codex-workflow-data/timeline/<task-id>.jsonl`; представления
Markdown, JSON и CSV можно создать повторно. Указывайте модель и метрики только
при наличии доверенного источника; иначе значения остаются недоступными.
Добавляйте только короткие очищенные сводки. Не включайте полные запросы,
скрытые рассуждения, учетные данные, токены или приватный текст журналов.
Очистка распознает распространенные секреты, но не все возможные секреты и
фрагменты запросов. Явная запись не обеспечивает автоматический сбор или
полную историю.

### `.codex/agents/` (подключается явно)

Флаг пользовательских агентов устанавливает девять проверенных TOML-файлов:

```text
.codex/agents/
  code-explorer.toml
  quick-implementer.toml
  implementer.toml
  luna-escalation.toml
  sol-architect.toml
  sol-architect-deep.toml
  code-validator.toml
  code-reviewer.toml
  commit-pusher.toml
```

Каждый файл определяет `name`, `description`, `developer_instructions`, `model`, `model_reasoning_effort` и `sandbox_mode`. Изменённые пользователем копии сохраняются при обновлении и удалении для ручной проверки.

### `docs/ai/PROJECT_CONTEXT.md`

Это редактируемый исходный шаблон. Он создаётся только при отсутствии существующего файла. После редактирования деинсталлятор обнаружит изменённый хэш и сохранит файл.

### `plans/TASK_TEMPLATE.md`

Это доступный проекту шаблон пакета задачи. Он также создаётся только при отсутствии и сохраняется после пользовательских изменений.

### Активный план и передача работы

Установка не создаёт `plans/ACTIVE_PLAN.md` и `plans/HANDOFF.md`. Они нужны только для активной нетривиальной задачи. При необходимости корневой оркестратор копирует шаблоны из `.codex-workflow/templates/`, заполняет их и остаётся единственным владельцем записи.

### Состояние и восстановление

- `.hybrid-codex-workflow-state.json` хранит версию пакета, целевой путь, версию Codex, управляемые файлы, хэши, владельцев, созданные каталоги, резервные копии и состояние блока `AGENTS.md`.
- `.hybrid-codex-workflow-transaction.json` существует только во время активной или прерванной транзакции.
- `.hybrid-codex-workflow-backups/` содержит точные резервные копии существующих файлов перед изменением.

Не редактируйте эти файлы вручную.

## Как процесс работает в вашем проекте

При запуске в проекте Codex обнаруживает корневой `AGENTS.md`. Управляемый блок требует прочитать контракты процесса и контекст проекта до выбора маршрута работы. Если были установлены пользовательские агенты, новый сеанс также загружает их TOML-файлы. После установки или обновления существующий сеанс необходимо перезапустить.

Песочница в TOML является значением по умолчанию. Права родительского сеанса и явные параметры запуска могут иметь приоритет, поэтому корневой агент должен проверять команды, изменения и доказательства, не считая изоляцию абсолютной.

```text
Ваш запрос
    |
    v
Корневой агент читает AGENTS.md, контракты и PROJECT_CONTEXT.md
    |
    v
Классифицирует задачу: простая, обычная или сложная/рисковая
    |
    +-- простая ------> ограниченная реализация и целевая проверка
    |
    +-- обычная ------> план -> реализация -> независимая валидация
    |
    `-- рисковая -----> исследование -> план -> реализация
                        -> валидация -> независимое ревью
    |
    v
Корневой агент принимает доказательства, интегрирует результат и завершает задачу
```

### Пример простой задачи

```text
Измени текст кнопки Save на Apply.
```

Ожидаемое поведение:

1. Классификация как простой задачи при отсутствии скрытых контрактных или безопасностных рисков.
2. Полный план не создаётся.
3. Выполняется ограниченное изменение.
4. Запускается целевая проверка.
5. Сообщается фактически наблюдавшийся результат.

### Пример обычной задачи

```text
Добавь REST endpoint с unit- и integration-тестами.
```

Ожидаемое поведение:

1. Прочитать соглашения API и команды из `PROJECT_CONTEXT.md`.
2. Классифицировать задачу как минимум как обычную.
3. Создать управляемые корневым агентом `plans/ACTIVE_PLAN.md` и `plans/HANDOFF.md`.
4. Определить область, владельца файлов, критерии приёмки, команды валидации и границы полномочий.
5. Выполнить ограниченную реализацию.
6. Провести независимую валидацию.
7. Завершить задачу только при наличии доказательства для каждого критерия.

### Пример рисковой задачи

```text
Измени авторизацию платежей и семантику сохранения данных.
```

Ожидаемое поведение:

1. Классифицировать как сложную задачу с высоким риском.
2. Исследовать контракты и риски до планирования.
3. Определить строгие границы владения и отката.
4. Реализовать только утверждённый план.
5. Провести независимую валидацию.
6. Потребовать независимое финальное ревью.
7. После замечаний повторить реализацию, валидацию и при необходимости ревью.

### Пример Git-публикации

```text
Закоммить эти изменения.
```

Это разрешает только локальный commit. Команда не разрешает push, force push, создание pull request, deployment, теги или удаление ветки. Для каждой такой операции требуется отдельная явная инструкция.

## Проверка установки

### Проверка файлов в Windows

Запустите из целевого проекта:

```powershell
$RequiredFiles = @(
    "AGENTS.md",
    ".codex-workflow\CODEX_WORKFLOW.md",
    ".codex-workflow\rules\ROUTING.md",
    ".codex-workflow\rules\VALIDATION.md",
    ".codex-workflow\rules\ESCALATION.md",
    ".codex-workflow\rules\GIT_SAFETY.md",
    ".codex-workflow\templates\PROJECT_CONTEXT.md",
    ".codex-workflow\templates\ACTIVE_PLAN.md",
    ".codex-workflow\templates\HANDOFF.md",
    ".codex-workflow\templates\TASK_TEMPLATE.md",
    "docs\ai\PROJECT_CONTEXT.md",
    "plans\TASK_TEMPLATE.md",
    ".hybrid-codex-workflow-state.json"
)

$MissingFiles = $RequiredFiles | Where-Object { -not (Test-Path -LiteralPath $_) }

if ($MissingFiles.Count -eq 0) {
    "PASS: installation files are present"
} else {
    "FAIL: installation files are missing"
    $MissingFiles
}
```

Если запрошены пользовательские агенты, из репозитория пакета проверьте исходный и установленный каталоги:

<!-- codex-current-target-example:begin -->
```powershell
python .\scripts\validate_agent_configs.py --codex-version 0.160.0
python .\scripts\verify_agent_runtime.py --target "C:\path\to\your-project"
```
<!-- codex-current-target-example:end -->

Первая команда проверяет девять исходных TOML-файлов. Вторая сравнивает установленный каталог с исходным: при полном совпадении файлов общий результат может быть `PASS`, но обнаружение остаётся `UNVERIFIED`, поскольку оно не запрашивалось.

Необязательная живая диагностика для тестового или некритичного проекта:

```powershell
python .\scripts\verify_agent_runtime.py --target "C:\path\to\your-project" --run-codex --evidence ".\agent-discovery.json"
```

Сохранённый результат миграции: для 0.160.0 параметр `--run-codex` отклоняется с UNSUPPORTED_RUNTIME_VERSION до обнаружения агентов. Capture и поведенческие проверки сохраняют привязку к 0.159.3. Миграция: 120 независимых тестов PASS, рецензия APPROVE; CLI установлен, но provenance BLOCKED, новые L0-L17 не приняты. См. [отчёт миграции](docs/validation/codex-0.160.0-windows.md).

Для исторических разрешённых версий параметр `--run-codex` пока запускает диагностическую пробу, а не сертификацию среды. Сохранённое окружение `0.159.0` не подтверждает версию `0.159.3`; одна проба не устанавливает runtime PASS. Для запуска пробы требуется отдельное разрешение на платное использование модели согласно плану живой проверки.

### Проверка обнаружения инструкций

```powershell
codex --cd "C:\path\to\your-project" --ask-for-approval never "Without editing files or running project commands, list the active AGENTS.md instruction files and summarize the Codex multi-agent workflow rules."
```

Ожидается, что Codex подтвердит:

- активен `AGENTS.md` целевого проекта;
- найдены контракты процесса и контекст проекта;
- состояние плана и передачи принадлежит корневому агенту;
- требуются наблюдаемые доказательства валидации;
- commit не означает push.

### Проверка идемпотентности

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project" -WithCustomAgents -WhatIf
```

Для неизменённой установки файлы и блок `AGENTS.md` должны иметь статус `UNCHANGED`. Повторный реальный запуск не дублирует блок и не перезаписывает неизменённый манифест.

## Обновление установки

1. Обновите локальный репозиторий пакета процесса.
2. Выполните `-WhatIf` или `--dry-run` для того же проекта.
3. Проверьте сообщения `UPDATE`, `UNCHANGED` и `PRESERVED MODIFIED FILE`.
4. Запустите установщик без режима просмотра, сохранив `-WithCustomAgents` или `--with-custom-agents` при обновлении пользовательских агентов.
5. Перезапустите Codex.
6. Повторите проверку обнаружения инструкций.

Установщик обновляет только файлы, которые всё ещё совпадают с ранее установленными хэшами. Изменённые файлы остаются нетронутыми. Перед обновлением существующего управляемого файла создаётся резервная копия.

## Восстановление прерванной операции

Не удаляйте `.hybrid-codex-workflow-transaction.json`: журнал содержит этапы операций, хэши и проверенные резервные копии. Незавершённая до фиксации транзакция восстанавливается откатом, а зафиксированная — завершением очистки. Если проблему нельзя безопасно разрешить, журнал и подтверждающие данные сохраняются.

Предварительный просмотр в Windows:

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project" -Recover -WhatIf
```

Восстановление:

```powershell
.\install.ps1 -TargetRepository "C:\path\to\your-project" -Recover
```

Linux/macOS:

```bash
bash ./install.sh --target "/path/to/your-project" --recover --dry-run
bash ./install.sh --target "/path/to/your-project" --recover
```

Установщик и деинсталлятор используют один механизм восстановления, поэтому записанную транзакцию можно восстановить любой из двух оболочек.

## Удаление в Windows

Откройте PowerShell в репозитории пакета процесса.

Для целевых репозиториев Windows используйте деинсталлятор PowerShell. Не передавайте путь Windows, например `C:\path\to\your-project`, в `bash ./uninstall.sh`: Bash может обработать обратные косые черты как управляющие символы и неверно определить целевой путь. Даже преобразованный путь `/mnt/c/...` может не пройти проверку безопасности манифеста, если процесс был установлен с использованием пути Windows. Для удаления используйте ту же среду PowerShell, в которой выполнялась установка.

### Шаг 1. Предварительный просмотр

```powershell
.\uninstall.ps1 -TargetRepository "C:\path\to\your-project" -WhatIf
```

Проверьте каждое сообщение `REMOVE` и `PRESERVED MODIFIED`.

### Шаг 2. Удаление

```powershell
.\uninstall.ps1 -TargetRepository "C:\path\to\your-project"
```

### Шаг 3. Проверка сохранённых файлов

Если все управляемые файлы оставались неизменёнными:

```text
PASS: Codex Multi-Agent Workflow uninstalled from C:\path\to\your-project
```

Если содержимое было изменено, оно сохраняется вместе с манифестом:

```text
WARN: uninstall preserved modified managed content; state manifest retained
```

Проверьте сохранённые файлы вручную. Не удаляйте контекст проекта, планы или изменённый блок `AGENTS.md`, пока не убедитесь, что они больше не нужны.

### Шаг 4. Новый сеанс Codex

После удаления перезапустите Codex, чтобы удалённый блок больше не входил в цепочку инструкций.

## Что удаляет деинсталлятор

Для каждого файла из манифеста деинсталлятор:

1. Проверяет точный управляемый путь.
2. Запрещает символические ссылки и выход за пределы проекта.
3. Вычисляет текущий SHA-256.
4. Удаляет файл только при совпадении хэша с установленным.
5. При несовпадении сохраняет файл и выводит предупреждение.
6. Удаляет блок `AGENTS.md` только при совпадении нормализованного хэша блока.
7. Сохраняет остальные инструкции `AGENTS.md`.
8. Удаляет только пустые каталоги, созданные установщиком.
9. Удаляет манифест только при отсутствии изменённого управляемого содержимого.

Деинсталлятор никогда рекурсивно не удаляет `docs/`, `plans/`, целевой проект или другой широкий каталог.

Управляемые пакетом пользовательские агенты удаляются только при совпадении хэшей. Изменённые и существовавшие до установки идентичные агенты сохраняются. Каталоги `.codex/agents/` и `.codex/` удаляются только тогда, когда их создал установщик и они пусты.

## Решение проблем

### Неподдерживаемая версия Codex

```text
FAIL: Unsupported Codex CLI ...
```

Файлы не изменены. Используйте проверенную версию или сначала обновите матрицу совместимости и тесты.

### `.codex-workflow` существует без манифеста

Установщик не может доказать владельца каталога. После проверки переместите его в другое место либо восстановите соответствующий `.hybrid-codex-workflow-state.json`. Не выполняйте принудительную перезапись.

### Неуправляемый пользовательский агент конфликтует с агентом пакета

Установщик не перезаписывает существующий `.codex/agents/<name>.toml`. Сравните его с версией пакета, переименуйте проектную роль или удалите файл после резервного копирования, затем повторите предварительный просмотр. Идентичный файл сохраняется и отмечается как существовавший ранее.

### Повреждённый манифест

Восстановите его из доверенной резервной копии. Без корректного состояния деинсталлятор не выполняет неопределённые удаления.

### Дублированный или повреждённый блок `AGENTS.md`

Проверьте начальный и конечный маркеры. Оставьте один полный блок и сохраните остальные инструкции проекта, затем повторите предварительный запуск.

### Изменённый файл сохраняется

Это ожидаемое безопасное поведение. Сравните его с исходником пакета или шаблоном в `.codex-workflow/templates/` и вручную выберите нужное содержимое.

### Обнаружена прерванная транзакция

Запустите восстановление с `-Recover` или `--recover`, сначала в режиме предварительного просмотра. Не удаляйте журнал и резервные копии до завершения восстановления.

### Codex не упоминает процесс

1. Убедитесь, что в корневом `AGENTS.md` есть ровно один управляемый блок.
2. Проверьте наличие `.codex-workflow/CODEX_WORKFLOW.md`.
3. Запустите Codex из правильного корня проекта или передайте `--cd`.
4. Перезапустите сеанс после изменения инструкций.
5. Попросите Codex перечислить активные инструкции без редактирования файлов.

Codex ищет проектные инструкции от корня проекта до текущего каталога. Более близкие инструкции имеют приоритет, поэтому вложенный `AGENTS.override.md` может переопределить общие правила.

### Codex не обнаруживает пользовательские агенты

1. Убедитесь, что установка выполнялась с `-WithCustomAgents` или `--with-custom-agents`.
2. Запустите `scripts/verify_agent_runtime.py` без `--run-codex`, чтобы проверить установленное содержимое.
3. Убедитесь, что проект доверенный: для недоверенного проекта Codex может пропустить проектную конфигурацию `.codex/`.
4. Начните новый сеанс из корня целевого проекта.
5. Запускайте необязательную диагностику `--run-codex` только после разрешения на платную живую проверку и проверьте очищенные от чувствительных данных доказательства. Считайте обнаружение `UNVERIFIED`, пока полная матрица L0–L17 для `0.159.3` не принята; это не runtime PASS.

## Рекомендуемый порядок внедрения

1. Сначала установите процесс в тестовый или некритичный проект.
2. Точно заполните `PROJECT_CONTEXT.md`.
3. [Проверьте обнаружение инструкций](#проверка-обнаружения-инструкций). Из корня целевого репозитория начните новый сеанс Codex и выполните проверку с запросом только на чтение из указанного раздела. Не разрешайте этой проверке изменять файлы или запускать команды проекта. Убедитесь, что Codex находит целевой `AGENTS.md`, контракты процесса и контекст проекта, указывает корневого агента владельцем состояния плана и передачи, требует прямые доказательства и различает commit и push. Эта проверка подтверждает только обнаружение инструкций и не означает runtime PASS для пользовательских агентов.
4. Проверьте текстовую классификацию простой задачи.
5. Выполните обычную задачу с планом и передачей работы.
6. Убедитесь, что доказательства валидации обычной задачи записаны. Установка не создаёт `plans/ACTIVE_PLAN.md` и `plans/HANDOFF.md`: проверяйте их, когда процесс создаёт эти файлы, а необязательный `plans/execution-log.jsonl` — только если задача использует этот журнал. Эти файлы принадлежат корневому агенту. Каждая задача и каждый критерий приёмки должны быть сопоставлены с точной командой валидации, её кодом завершения, кратким существенным наблюдением или путём к артефакту, честным результатом `PASS`, `FAIL` или `BLOCKED`, а также отметкой времени, если процесс её записывает. Доказательства должны быть очищены от чувствительных данных и не содержать секретов. Для обычных и сложных задач также нужны доказательства независимого валидатора, а для работ, требующих проверки высокого риска, — вердикт рецензента. При отсутствии обязательных доказательств задача не завершена.

   Проверка только на чтение в PowerShell из корня целевого проекта (запускайте `Get-Content` только для найденных файлов):

   ```powershell
   if (Test-Path -LiteralPath '.\plans\ACTIVE_PLAN.md') {
       Get-Content -LiteralPath '.\plans\ACTIVE_PLAN.md'
   }
   if (Test-Path -LiteralPath '.\plans\HANDOFF.md') {
       Get-Content -LiteralPath '.\plans\HANDOFF.md'
   }
   if (Test-Path -LiteralPath '.\plans\execution-log.jsonl') {
       Get-Content -LiteralPath '.\plans\execution-log.jsonl'
   }
   ```

   Эквивалент для POSIX:

   ```bash
   test -f plans/ACTIVE_PLAN.md && sed -n '1,240p' plans/ACTIVE_PLAN.md
   test -f plans/HANDOFF.md && sed -n '1,240p' plans/HANDOFF.md
   test -f plans/execution-log.jsonl && sed -n '1,240p' plans/execution-log.jsonl
   ```
7. Проверьте разрешение commit-only без push.
8. Просмотрите удаление и убедитесь, что изменённый контекст сохраняется.
9. Только после успешного пилота устанавливайте процесс в другие репозитории.
